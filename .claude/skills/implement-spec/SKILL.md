# Реализация спеки

Аргумент — номер спеки `NNN`. Файл: `docs/spec/NNN-*.md`.

## 1. Подготовка

1. Прочитай `CLAUDE.md`, `docs/spec/README.md`, `docs/spec/glossary.md` и саму спеку целиком.
2. Проверь `status`:
   - `ready` — продолжай;
   - `in-progress` — продолжи с первой неотмеченной задачи;
   - `blocked` — проверь, ответил ли человек на все вопросы раздела 9 (отмечены `[x]` и есть ответ). Если нет — остановись и перечисли неотвеченные вопросы;
   - `draft`, `review`, `done`, `superseded` — не начинай, сообщи статус и остановись.
3. Проверь `depends_on`: все перечисленные спеки должны быть `done`. Иначе — остановись и назови недостающие.
4. Прочитай спеки из `depends_on` (разделы 4 «Контракты») — твой код должен с ними совпадать.
5. Проверь `docs/spec/questions.md` и `docs/spec/notes.md`: если там остался пункт, у которого «куда»/«когда» — эта спека, значит при черновике его не забрали — это пробел (шаг 4).
6. Пройди спеку на пробелы до начала кода: каждый AC проверяем? Контракты достаточны, чтобы писать код без догадок? Нашёл пробел — сразу `blocked` (шаг 4), код не пиши.

## 2. Старт

1. Ветка первого этапа от свежей основной ветки (см. «Ветка на этап» ниже).
2. Во frontmatter: `status: in-progress`, `updated: <сегодня>`. Коммит `chore: spec:NNN взята в работу` — первым в ветке первого этапа.

## 3. Задачи — по порядку, по одной

### Разбивка на этапы и субагенты

Спека реализуется не в одном большом контексте. Основной агент — дирижёр: подготовка (шаг 1), старт (шаг 2), разбивка, решения о блокировке, завершение (шаг 5) и отчёт. Код пишут и проверяют субагенты.

1. **Разбей задачи на этапы.** Этап — одна задача `T-n` или несколько мелких связанных задач, на несколько часов работы, с понятным результатом: какие REQ/AC закрыты, какие пакеты затронуты. Порядок — как в разделе 8 спеки. Составь план этапов до первого кода.
2. **Реализация этапа — отдельный субагент на Haiku** (`model: "haiku"`). Бриф самодостаточный, субагент не видит твой контекст: номер и путь спеки, задачи этапа с их REQ/AC, нужные выдержки из раздела 4 «Контракты», затронутые пакеты, что сделано в прошлых этапах (коммиты, новые имена), правила ниже (тест на AC, README, глоссарий, `D-n`/`N-n`, формат коммита), ограничения окружения. Субагент делает этап по шагам 1–4 ниже и коммитит. Нашёл пробел в спеке — не додумывает, а возвращает вопрос: блокировку (шаг 4) делает основной агент.
3. **Ревью этапа — отдельный субагент на Sonnet** (`model: "sonnet"`), не тот, что писал код. Входные данные: диапазон коммитов этапа и задачи с REQ/AC. Проверяет: каждый AC этапа закрыт тестом с id в имени, и тест действительно проверяет критерий; код совпадает с контрактами спеки и зависимостей; границы ядра и оболочки; ничего сверх спеки; README и глоссарий обновлены. Возвращает список замечаний с `файл:строка`, только чтение, без правок.
4. **Замечания ревью** исправляет новый субагент на Haiku по списку, отдельным коммитом `fix: spec:NNN T-n замечания ревью`. Повторное ревью — только по исправленным пунктам.
5. **Контроль качества.** Результат субагента проверяй сам: коммиты на месте, тесты этапа зелёные, отчёт не поверхностный. Поверхностный результат — перезапусти Haiku с более подробным брифом. Не помогло — тот же этап на Sonnet.
6. Субагенты запускаются по одному на этап, последовательно: этапы зависят друг от друга, и коммиты в одной ветке не должны пересекаться.

### Ветка на этап

Каждый этап начинается от свежей основной ветки, в которую уже влиты все предыдущие этапы спеки:
1. `git fetch`, ветка `spec/NNN-tN` (для этапа из нескольких задач — по первой: `spec/NNN-t7`) от `origin/main`. Следующий этап не начинается, пока PR предыдущего не влит в `main`.
2. PR этапа — в `main`. Поэтому каждый этап оставляет `main` рабочим: `npm run check` зелёный на ветке этапа до слияния.

**Связанные задачи — через промежуточную фича-ветку.** Если по разделу 8 задача ломает соседний пакет, который чинят только следующие задачи, `main` между ними был бы сломан. Такие задачи — группа:
1. Фича-ветка `spec/NNN-<тема>` (например `spec/022-swarm-agent`) от свежей `main`, push.
2. Каждая задача группы — свой этап: ветка `spec/NNN-tN` от свежей фича-ветки, PR в фича-ветку. Внутри группы `npm run check` может быть красным там, где ждёт следующих задач группы; тесты самой задачи — зелёные.
3. Когда группа готова — долить свежую `main` в фича-ветку, `npm run check` и CI зелёные, PR фича-ветки в `main`. Следующий этап вне группы — от свежей `main` после этого слияния.
4. Группу и причину запиши в журнал реализации до первого этапа группы.
3. Push, PR и слияние — по команде человека. Если человек велел сливать самому — сливай после зелёного `npm run check` и CI.

Если ты сам запущен как субагент и инструмента Agent у тебя нет, делай этапы последовательно в своём контексте. Ревью тогда — отдельный проход по диффу этапа перед следующим этапом.

### Шаги задачи

Для каждой задачи `T-n`:
1. Реализуй только то, что закрывает её REQ/AC.
2. Тесты: на каждый AC задачи тест с id в имени (`it('AC-NNN-k: ...')`). Сначала тест, который падает, потом код.
3. Прогони тесты затронутых пакетов и `npm run typecheck`. Обнови `README.md` каждого пакета, который задача создала или изменила (схема — правило 7 в `CLAUDE.md`): запиши ключевые решения задачи с причиной (библиотека и версия, устройство порта или адаптера, формат данных, отклонение, трактовка) и перепиши устаревшее под новое состояние — README описывает пакет сейчас, а не историю. Если в коде появилось имя (тип, порт, событие, статус), которого нет в `docs/spec/glossary.md`, — добавь его в глоссарий в том же коммите и отметь в журнале (правило 5 в `CLAUDE.md`).
4. Отметь `[x]` у задачи. Коммит `feat|fix|chore: spec:NNN T-n <что сделано>` (на русском).

Если в процессе обнаружилось, что спека неполна или противоречива — шаг 4.

Если вопрос не мешает текущей задаче (решение нужно в другой спеке, или ты принял трактовку, которую должен подтвердить человек), — не блокируйся: запиши `D-n` в `docs/spec/questions.md` по формату из его шапки (откуда, куда, варианты) и продолжай. Трактовку дополнительно отметь в журнале реализации.

Заметил мелкое улучшение или технический долг за пределами спеки (выбирать нечего, просто стоит сделать позже) — не делай, а запиши `N-n` в `docs/spec/notes.md`: где, когда взять в работу, что сделать.

## 4. Блокировка

1. Допиши в раздел 9 вопрос: `- [ ] **Q-k.** <конкретный вопрос, варианты ответа и их последствия> *(Claude, дата)*`.
2. `status: blocked`, `updated: <сегодня>`. Коммит `chore: spec:NNN заблокирована: Q-k`.
3. Остановись и сообщи пользователю вопрос. Не продолжай другие задачи, если они зависят от ответа.

## 5. Завершение

1. Ветка завершения — от свежей основной ветки, как этап. Полный прогон: `npm run check`. Всё зелёное. (Пока реализуется сама спека 000 и `npm run check` ещё нет — прогнать те команды, что уже есть.)
2. Критерии `[manual]`: выполни проверку, если она возможна локально, и приложи результат в журнал. Невозможна (например, нужен CI) — так и напиши в журнале.
3. Журнал реализации: строка с датой, веткой и последним коммитом, кратко что сделано, все отклонения от спеки с причинами.
4. NFR: если есть измеримые — приложи замеры в журнал.
5. Сверь README всех затронутых пакетов с кодом: «что внутри сейчас», ключевые решения, ограничения и связи соответствуют реализации, устаревшего нет.
6. `status: review`, `updated: <сегодня>`. Обнови статус в реестре `docs/spec/README.md`. Коммит `chore: spec:NNN готова к ревью`.
7. Отчёт пользователю: таблица AC → тест (файл:строка) → результат; отклонения; что проверено вручную и что не проверено; новые `D-n` в `questions.md` — отдельно те, что нужно решить при приёмке этой спеки; новые `N-n` в `notes.md`.

Push и merge request — только по команде пользователя.
