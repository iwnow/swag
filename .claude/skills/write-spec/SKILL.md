# Черновик спеки

## Шаги

1. Прочитай `docs/spec/README.md` (процесс, реестр), `docs/spec/_template.md`, `docs/spec/glossary.md`, `AI_PLATFORM_ROADMAP.md` и спеки, от которых будет зависеть новая (их раздел 4 «Контракты»).
2. Номер: если тема есть в реестре — его номер; иначе следующий свободный. Файл `docs/spec/NNN-slug.md`, slug — латиницей, через дефис.
3. Заполни шаблон, `status: draft`:
   - **Коротко** — блок для человека в начале: что появится, ключевые решения, что нужно от человека. Читается за минуту без остальной спеки.
   - **Контекст** — ссылка на раздел роадмапа, текущее → целевое состояние.
   - **Не входит** — явно перечисли соседние темы, которые уйдут в другие спеки.
   - **Требования** — проверяемые, с MUST/SHOULD. Без слов «быстро», «удобно» без числа.
   - **Контракты** — точные типы/схемы Zod, эндпоинты, события, таблицы, env. Согласованы с контрактами зависимостей.
   - **Критерии приёмки** — given/when/then, каждый автоматизируемый; иначе `[manual]` с описанием проверки. Покрывают каждое MUST-требование.
   - **Безопасность** — что не должно сломаться и каким AC это проверяется.
   - **Задачи** — упорядоченные, каждая со ссылками на REQ/AC и критерием готовности. Декомпозиция мелкая: каждую задачу должен выполнить субагент на слабой модели (Haiku) по одному брифу, без собственных архитектурных решений. Ориентир — один пакет или одна связная правка в 1–3 файлах, заранее названные файлы, контракты и тесты, которые она закрывает. Задача, где нужно выбирать между вариантами или трогать несколько пакетов сразу, дробится дальше.
4. **Разбор бэклога.** Прочитай целиком `docs/spec/questions.md` (`D-n`) и `docs/spec/notes.md` (`N-n`) и реши по каждому пункту, забирать ли его в эту спеку:
   - **забрать обязательно** — у пункта «куда»/«когда» указана эта спека;
   - **забрать, если можно решить сейчас** — пункт касается тех же пакетов или области, что и спека, не зависит от будущих спек и не раздувает её больше чем на пару задач;
   - **оставить** — всё остальное, с короткой причиной для отчёта.

   Забранный пункт:
   - `D-n` → вопрос `Q-k` в разделе 9 со ссылкой «из D-n» (решение принимает человек, как по любому вопросу спеки);
   - `N-n` → задача `T-k` в разделе 8 со ссылкой «из N-n»; если пункт меняет поведение — ещё требование и критерий приёмки;
   - затем **удали пункт** из `questions.md` или `notes.md`. Номер не переиспользуется, история остаётся в git и в ссылке «из D-n / N-n» в спеке.

   Прочитай `docs/spec/scenarios.md` (`S-n`). Сценарий, который эта спека разблокирует (остальные спеки из его шапки уже готовы), — шаги в критерии `[manual]` или в автотест со ссылкой «из S-n», статус сценария обнови. Сценарии из файла не удаляются.
5. Всё, что требует решения человека (выбор технологии, бизнес-правило, число-порог, которого нет в роадмапе), — в **Открытые вопросы**: вопрос, варианты, твоя рекомендация с причиной. Не выбирай молча.
6. Новые имена — термины, типы, порты, события, статусы — добавляй в `glossary.md` по мере появления в черновике, а не в конце. В самопроверке сверь: каждое новое имя из разделов 4–5 есть в глоссарии.
7. Добавь или обнови строку в реестре `docs/spec/README.md` со статусом `draft`.
8. Самопроверка перед сдачей:
   - каждое MUST покрыто хотя бы одним AC;
   - каждый AC закрыт какой-то задачей;
   - каждую задачу Haiku выполнит по брифу: файлы и контракты названы, выбирать нечего;
   - по контрактам можно писать код без догадок;
   - «Не входит» не пуст;
   - в `questions.md` и `notes.md` не осталось пунктов, адресованных этой спеке;
   - у каждого забранного пункта есть `Q-k` или `T-k` со ссылкой «из D-n / N-n».
9. Сообщи пользователю: путь к спеке, сколько требований и критериев, список открытых вопросов; что забрано из бэклога (`D-n` → `Q-k`, `N-n` → `T-k`) и что оставлено с причиной. Если человек решит не брать пункт в эту спеку — верни его в файл с прежним номером. Статус `ready` ставит только человек.
