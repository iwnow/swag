# Спецификации продукта

Разработка идёт от спецификаций: человек пишет спеку, агент по ней реализует код и тесты, человек принимает результат. Спека — единственный источник требований. Чего нет в спеке, агент не делает. Если в спеке противоречие или пробел, агент не додумывает, а останавливается и задаёт вопрос.

Верхний уровень — [роадмап](../../AI_PLATFORM_ROADMAP.md): что и зачем. Спеки — как именно, с точностью до контрактов и критериев приёмки.

## Структура

```
docs/spec/
├── README.md          # этот файл: процесс + реестр спек
├── _template.md       # шаблон новой спеки
├── glossary.md        # термины и их имена в коде
├── questions.md       # отложенные вопросы из реализации: решаются в будущих спеках
├── notes.md           # мелкие улучшения и технический долг: делаются, когда трогаем это место
└── NNN-slug.md        # спеки, номер по порядку создания
```

Одна спека — один законченный кусок поведения, который можно принять целиком. Ориентир — от одного до нескольких дней работы агента. Этап роадмапа обычно занимает 1–3 спеки.

## Жизненный цикл

| Статус | Кто ставит | Что значит |
|---|---|---|
| `draft` | автор | Пишется. Есть открытые вопросы. Агент не берёт. |
| `ready` | человек | Вопросов нет, контракты и критерии приёмки зафиксированы. Можно отдавать агенту. |
| `in-progress` | агент | Агент взял в работу, ветка `spec/NNN-slug`. |
| `blocked` | агент | Нашёл пробел или противоречие, записал в «Открытые вопросы», ждёт человека. |
| `review` | агент | Все задачи сделаны, все проверки зелёные, журнал заполнен. |
| `done` | человек | Принято, влито. |
| `superseded` | человек | Заменена другой спекой (указать какой в `superseded_by`). |

Требования меняет только человек. Когда спека в `in-progress`, правка требований возвращает её в `ready`, и агент сверяет сделанное с новой версией.

## Правила написания спеки

1. **Требования проверяемые.** Каждое требование `REQ-NNN-n` сформулировано так, чтобы его можно было проверить. Слова «быстро», «удобно», «надёжно» без числа не допускаются.
2. **Критерии приёмки — given / when / then.** У каждого `AC-NNN-n` есть автотест, а в имени теста стоит id критерия: `it('AC-001-3: бюджет роя отклоняет вызов сверх лимита', ...)`. Если автотест невозможен, критерий помечается `[manual]` с описанием ручной проверки.
3. **Контракты — точные.** Типы, схемы Zod, форматы событий, эндпоинты, имена env-переменных пишутся в спеке, а не «на усмотрение агента».
4. **Явные границы.** В разделе «Не входит» перечислено, что агент делать не должен, даже если кажется логичным.
5. **Безопасность.** Отдельно записано, что не должно сломаться и как это проверить.
6. **Задачи — упорядоченный список.** Каждая задача ссылается на REQ/AC, которые закрывает, и имеет свой критерий готовности.
7. **Имена — из [глоссария](glossary.md).** Новый термин сначала добавляется туда.
8. **Нет открытых вопросов — можно ставить `ready`.**

## Цикл работы со спекой

| Шаг | Кто | Что делается | Результат |
|---|---|---|---|
| 1. Черновик | человек или агент | `/write-spec <тема>` — шаблон в статусе `draft`, всё неясное вынесено в открытые вопросы с рекомендациями | `draft` |
| 2. Закрытие вопросов | человек | Читает «Коротко», отвечает на вопросы раздела 9, ставит статус | `ready` |
| 3. Реализация | агент, отдельная сессия | `/implement-spec NNN`: ветка `spec/NNN-slug`, задачи по порядку, коммит на задачу, тест на каждый AC | `in-progress` |
| 4. Блокировка (если нужно) | агент → человек | Агент записывает вопрос `Q-n` и останавливается; человек отвечает в спеке, агент продолжает тем же `/implement-spec NNN` | `blocked` → `in-progress` |
| 5. Сдача | агент | `npm run check` зелёный, ручные проверки и замеры NFR в журнале, отчёт «AC → тест → результат» | `review` |
| 6. Приёмка | человек | Сам запускает `npm run up` и `npm run check`, смотрит дифф (можно `/code-review`), проверяет ручные AC | замечания → шаг 3 |
| 7. Влитие | человек (или агент по команде) | Ветка вливается в `main`, статус в спеке и в реестре | `done` |

Пока агент делает спеку N, следующую можно готовить шагами 1–2.

**Вопросы бывают двух видов.**
- `Q-n` в разделе 9 спеки — блокирует её: без ответа спека не станет `ready`, а агент в работе ставит `blocked`.
- `D-n` в [questions.md](questions.md) — не блокирует текущую спеку: решение отложено до спеки, где оно понадобится, или нужно подтверждение принятой агентом трактовки. `D-n`, адресованные приёмке спеки, человек решает на шаге 6.

**Заметки** `N-n` в [notes.md](notes.md) — мелкие улучшения и технический долг, где выбирать нечего: их записывают агент при реализации и ревьюер при приёмке.

**Бэклог разбирается с каждой новой спекой.** `questions.md` и `notes.md` — очередь, которая должна убывать. На шаге 1 `/write-spec` просматривает оба файла целиком и забирает в новую спеку всё, что адресовано ей, и всё, что можно решить сейчас в её области без зависимости от будущих спек: `D-n` становится вопросом `Q-k`, `N-n` — задачей `T-k`, со ссылкой «из D-n / N-n». Забранный пункт из файла удаляется; номера не переиспользуются, история — в git и в спеке. В отчёте о черновике видно, что забрано и что оставлено и почему. Если человек не хочет брать пункт в эту спеку, пункт возвращается в файл.

Реализацию лучше запускать в отдельной сессии от обсуждения: в ней только спека и код, без истории споров. Push, merge request и влитие — только по команде человека.

Скилл [implement-spec](../../.claude/skills/implement-spec/SKILL.md) проводит агента по шагам 3–5, [write-spec](../../.claude/skills/write-spec/SKILL.md) — по шагу 1. Правила для агента — в [CLAUDE.md](../../CLAUDE.md).

**Особенность спеки 000.** `npm run check` и `spec:check` появляются в ней самой, поэтому до их появления агент прогоняет те команды, что уже есть. Для AC-000-15 (зелёный CI) до запуска нужен репозиторий на GitHub и push основной ветки.

## Трассировка

`npm run spec:check` (появится в спеке 000) проверяет: у каждого AC спек в статусах `in-progress`, `review`, `done` есть тест с этим id, кроме критериев с пометкой `[manual]`. Проверка входит в CI.
