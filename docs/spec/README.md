# Спецификации продукта

Разработка идёт от спецификаций: человек пишет спеку, агент по ней реализует код и тесты, человек принимает результат. Спека — единственный источник требований. Чего нет в спеке, агент не делает. Если в спеке противоречие или пробел, агент не додумывает, а останавливается и задаёт вопрос.

Верхний уровень — [роадмап](../../AI_PLATFORM_ROADMAP.md): что и зачем. Спеки — как именно, с точностью до контрактов и критериев приёмки.

## Структура

```
docs/spec/
├── README.md          # этот файл: процесс + реестр спек
├── _template.md       # шаблон новой спеки
├── glossary.md        # термины и их имена в коде
└── NNN-slug.md        # спеки, номер по порядку создания
```

Одна спека — один законченный кусок поведения, который можно принять целиком. Ориентир — от одного до нескольких дней работы агента. Этап роадмапа обычно занимает 1–3 спеки.

## Жизненный цикл

| Статус | Кто ставит | Что значит |
|---|---|---|
| `draft` | автор | Пишется. Есть открытые вопросы. Агент не берёт. |
| `ready` | человек | Вопросов нет, контракты и критерии приёмки зафиксированы. Можно отдавать агенту. |
| `in-progress` | агент | Агент взял в работу, ветка `spec/NNN-slug`. |
| `blocked` | агент | Нашёл пробел или противоречие, записал в «Открытые вопросы», ждёт человека. |
| `review` | агент | Все задачи сделаны, все проверки зелёные, журнал заполнен. |
| `done` | человек | Принято, влито. |
| `superseded` | человек | Заменена другой спекой (указать какой в `superseded_by`). |

Требования меняет только человек. Когда спека в `in-progress`, правка требований возвращает её в `ready`, и агент сверяет сделанное с новой версией.

## Правила написания спеки

1. **Требования проверяемые.** Каждое требование `REQ-NNN-n` сформулировано так, чтобы его можно было проверить. Слова «быстро», «удобно», «надёжно» без числа не допускаются.
2. **Критерии приёмки — given / when / then.** У каждого `AC-NNN-n` есть автотест, а в имени теста стоит id критерия: `it('AC-001-3: бюджет роя отклоняет вызов сверх лимита', ...)`. Если автотест невозможен, критерий помечается `[manual]` с описанием ручной проверки.
3. **Контракты — точные.** Типы, схемы Zod, форматы событий, эндпоинты, имена env-переменных пишутся в спеке, а не «на усмотрение агента».
4. **Явные границы.** В разделе «Не входит» перечислено, что агент делать не должен, даже если кажется логичным.
5. **Безопасность.** Отдельно записано, что не должно сломаться и как это проверить.
6. **Задачи — упорядоченный список.** Каждая задача ссылается на REQ/AC, которые закрывает, и имеет свой критерий готовности.
7. **Имена — из [глоссария](glossary.md).** Новый термин сначала добавляется туда.
8. **Нет открытых вопросов — можно ставить `ready`.**

## Как отдать спеку агенту

В Claude Code в этом репозитории:

```
/implement-spec 000
```

Скилл [implement-spec](../../.claude/skills/implement-spec/SKILL.md) проводит агента по процессу: проверка статуса → ветка → задачи по порядку → тесты на каждый AC → проверки → журнал → `review`. Правила для агента — в [CLAUDE.md](../../CLAUDE.md).

Новую спеку из этапа роадмапа помогает набросать `/write-spec <тема>`: агент заполняет шаблон в статусе `draft` и выносит всё неясное в открытые вопросы.

## Трассировка

`pnpm spec:check` (появится в спеке 000) проверяет: у каждого AC спек в статусах `in-progress`, `review`, `done` есть тест с этим id, кроме критериев с пометкой `[manual]`. Проверка входит в CI.
