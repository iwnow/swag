# Сценарии тестирования

Сквозные сценарии проверки платформы глазами пользователя: на поднятом локально контуре, через UI и API, поверх нескольких спек. Сценарий записывается, как только понятно, что проверять, даже если нужных спек ещё нет. Цель — постепенно превратить каждый сценарий в автотест, который прогоняется на контуре целиком.

Чем отличается от соседних файлов: критерии `AC-NNN-n` проверяют одну спеку, [notes.md](notes.md) и [questions.md](questions.md) — очереди, которые убывают. Сценарии не удаляются: они накапливаются и остаются регрессионным набором.

Формат: `S-n` — номер по порядку, не переиспользуется. В шапке:
- **Спеки** — без каких спек сценарий не пройти;
- **Модели** — free, фейк или платные. По умолчанию — только free-модели (`:free`) или фейк; платные — только явно и только дешёвые;
- **Статус** — `ждёт спек` (нужных спек ещё нет), `ручной` (выполним руками), `авто` (есть автотест; путь к нему рядом).

При черновике спеки `/write-spec` смотрит сценарии, которые эта спека разблокирует, и берёт их шаги в критерии `[manual]` или в автотест. Сценарий при этом остаётся здесь, меняется только его статус.

## Сценарии

### S-1. Регистрация компании и вход в платформу

*Спеки: 012, 024, 014. Модели: не нужны. Статус: шаги 1 (API без токена), 7–10 на уровне HTTP — автотест 024 (AC-024-24, `apps/api/test/stack.test.ts`), прогон 2026-10-31 зелёный, блокировка в api за 1950–4825 мс (NFR-024-1, два прогона); шаг 1 в UI и вход пользователя в кабинет — ручная проверка AC-024-26. Шаги 1–5, 7, 9, 10 в браузере (регистрация, приглашение, админка, блокировка, супервизор) — ручные AC-014-11…14 спеки 014, пройдены 2026-11-01 (журнал 014, T-14…T-16 и T-20); шаг 8 в браузере — супервизор видит обе организации, изоляция данных — автотест 024. На уровне HTTP также покрыто автотестом 012 (AC-012-27, `apps/identity/test/stack.test.ts`): шаг 2 (письмо), шаг 3 (подтверждение, админ, вход в сессию), шаг 4 только вторая ссылка (повтор регистрации — AC-012-5), шаг 5 вход по верному паролю и выход, шаг 10 — вход супервизора. Шаг 5 с неверным паролем и шаг 6 (argon2id) — AC-012-12 и AC-012-6/23, не стек-тест. От человека, 2026-10-27.*

Подготовка: контур поднят локально (`npm run up`), отправка почты — тестовым адаптером порта почты, письма читаются из него.

1. Без входа открыть UI: доступны только регистрация и вход, любой другой адрес ведёт на вход; запрос к API с данными организации без токена — `401`.
2. Зарегистрировать компанию: ввести email в форму регистрации → приходит письмо с подтверждением.
3. Перейти по ссылке из письма, задать пароль → попасть в личный кабинет новой организации. Пользователь — администратор этой организации.
4. Повторная регистрация на тот же email не создаёт вторую организацию; ссылка из письма второй раз не срабатывает.
5. Выйти, войти по email и паролю → снова кабинет своей организации. Неверный пароль — отказ без подсказки, существует ли email.
6. В БД пароль хранится только хэшем argon2id.
7. Администратор добавляет пользователя с ролью `user`; тот входит и видит только свою организацию.
8. Зарегистрировать вторую компанию: её пользователь не видит процессов, роёв, событий и операций первой; запрос к чужим данным по API отклоняется.
9. Заблокированный пользователь не может войти, его действующий токен перестаёт работать.
10. Первый супервизор (создан при развёртывании) входит и видит обе организации.

### S-2. Баланс ИИ учитывает вызовы платных моделей

*Спеки: 012, 024 (тестовый пользователь), 013 (пополнение), 025 (баланс ИИ). Модели: free, затем дешёвые платные. Статус: ждёт спек. От человека, 2026-10-27.*

Это единственный сценарий, где осознанно вызываются платные модели, — и только дешёвые.

Подготовка: контур поднят локально (`npm run up`) на профиле с free-моделями (`LLM_PROFILE=dev`), ключ OpenRouter в `.env.llm`. Тестовый пользователь и организация — из S-1 или из seed.

1. Виртуально пополнить баланс ИИ организации на небольшую сумму, например $1.
2. Запустить рой или процесс бота, сделать несколько вызовов: в событиях `llm.call` стоимость 0, баланс не изменился.
3. Переключить контур на дешёвые платные модели без правки кода: профиль `test-pay` (спека 032): дешёвые платные модели OpenRouter без reasoning; порог цены записан в профиле.
4. Повторить вызовы: в `llm.call` стоимость больше 0, баланс уменьшился ровно на сумму стоимостей вызовов, расход виден в кабинете по узлам и процессам.
5. Довести остаток до нуля или выставить маленький баланс: следующий вызов отклоняется до обращения к провайдеру.
6. Вернуть контур на free-модели.

Что понадобится сделать для сценария: профиль дешёвых платных моделей, способ переключить профиль на поднятом контуре, seed тестового пользователя с балансом.


### S-3. Рой с LLM решает задачу вместе

*Спеки: 002, 022, 030. Модели: free. Статус: ручной (022, T-17: AC-022-26, NFR-022-2; 030: AC-030-11). Claude, 2026-10-28.*

Подготовка: контур поднят локально (`npm run up`) с `LLM_PROFILE=dev`, ключ OpenRouter в `.env.llm`.

1. В UI создать рой: «Автор» (`chat-small`) пишет четверостишие на тему задачи, «Редактор» (`chat-small`) проверяет и правит текст и возвращает автору.
2. Задача — «четверостишие про осень». Запустить.
3. В ленте видны шаги агентов, сообщения между ними и вызовы модели с токенами, стоимость 0.
4. Граф показывает рёбра в обе стороны с числом сообщений.
5. Рой завершается до `SWARM_TIMEOUT_MS`, результат — четверостишие.
6. Из события в UI открывается трейс в Grafana: ходы агентов и вызовы gateway внутри них.
7. После роя `docker ps -a --filter label=swag.kind` пуст.
8. Ответ участника обработан ходом получателя: после `bus.message` к агенту в ленте есть его `agent.working` с тем же `messageId`, отметок «не прочитано» у сообщений к `agent-1` нет (030).
