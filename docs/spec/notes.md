# Заметки на будущее

Мелкие улучшения и технический долг, замеченные при реализации и ревью спек. Решения человека не требуют, работу не блокируют: это то, что стоит сделать, когда будем трогать соответствующее место. Вопросы, где нужен выбор, — в [questions.md](questions.md), а не здесь.

Формат: `N-n` — номер по порядку, не переиспользуется. Где — файл или область. Когда — момент, когда заметку взять в работу (спека из [реестра](README.md#реестр-спек) или событие: «при добавлении нового пакета»). 

Жизненный цикл: при черновике каждой новой спеки `/write-spec` забирает отсюда заметки, которые можно сделать в её области, превращает их в задачи `T-k` со ссылкой «из N-n» и удаляет отсюда. Здесь остаётся только то, до чего ещё не дошли ([процесс](README.md#цикл-работы-со-спекой)).

Самопроверка агента внутри цикла — параметр агента.** *(от человека, 2026-10-29; где — `packages/agent-core` (`runAgentLoop`, ход агента роя), `AgentDraft` в `packages/contracts`, форма роя в `ui-core` и `apps/ui/cabinet`; когда — после 015 (eval): сначала замер, потом спека; Claude, 2026-10-29)*

Платформа не просит модель проверить ответ по роли и не знает, достигнута ли цель. Доработка сейчас возможна только диалогом агентов, если роли так написаны.   Прогон «только роли и диалог» на `dev` (2026-10-29, S-3 с ролями «Редактор возвращает замечания, Автор правит до „одобрено“», 3 роя): механика работает — в рое `b941b141` три круга Автор ↔ Редактор, замечания Редактора по существу (рифма, размер, тавтология); но Автор на `chat-small` качество не поднял, до «одобрено» не дошло, рой упал на 4-м ходу Автора с `model_error:max_tokens` (N-14) через 253 с.   Вопросы для спеки и рекомендации:
  1. **Контекст проверки.** Вся история агента, как у напоминания агенту-входу (`agent-core/src/index.ts`: первый проход дописывается в `history`, второй идёт с ней и новым сообщением) — дёшево за счёт кэша промпта, модель видит прошлые замечания; минус — склонна подтвердить свой ответ. Альтернатива — чистый контекст «критика» (роль, входящее сообщение, черновик): независимее, но без кэша и без истории обсуждения. Рекомендация — вся история; чистый контекст — второй вариант в замере.
  2. **Где перехватывать черновик.** `send_message` исполняется сразу и уступает ход, проверка после отправки дала бы получателю две версии. Рекомендация — задержать исполнение: вызовы `send_message` и `finish` первого прохода не исполняются, модель получает их как черновик с инструкцией проверки, исполняется ответ второго прохода. Меняет правило 4.2 спеки 022 «инструменты исполняются сразу» — главное изменение спеки.
  3. **Сколько проверок.** Рекомендация — одна за ход, без цикла «проверяй, пока не подтвердишь»: повтор без внешнего сигнала качество не поднимает, а стоимость растёт линейно.
  4. **Что проверяется.** Рекомендация — только черновики `send_message` и `finish`; ответ текстом без инструмента — не черновик, его ведут напоминание входу и N-17.
  5. **Ответ второго прохода.** Подтвердил — повторил тот же вызов; исправил — другой вызов; ответил текстом — исполняется черновик первого прохода (проверка не должна терять готовый ответ). Рекомендация — так; ошибка модели во втором проходе — `model_error`, как обычно.
  6. **Параметр.** `selfCheck: boolean` в `AgentDraft`, по умолчанию `false`, флажок «Самопроверка» в форме роя у каждого агента; в env агента — `AGENT_SELF_CHECK`. Рекомендация — так, без уровня роя: включать точечно на агентах, чей ответ дорого испортить (вход, редактор).
  7. **Шаги и деньги.** Проход проверки — обычный вызов модели: `steps + 1`, учёт в `AGENT_MAX_STEPS`, `llm.call` и бюджет 004. Рекомендация — так, без отдельного лимита.
  8. **Видимость.** `agent.step` прохода проверки с признаком `selfCheck: true` и строкой в ленте «проверка: подтвердил / исправил» — иначе в UI не видно, работает ли параметр. Рекомендация — так; доля «исправил» — метрика для замера.
  9. **Замер до спеки.** На eval-наборе (015) сравнить качество и стоимость: без проверки, проверка со всей историей, проверка в чистом контексте — на `chat-small` и сильной модели. Не выигрывает ни один вариант — параметр не вводить, заметку закрыть.

- [ ] **N-27. Production-развёртывание UI: один nginx, папка на фронтенд.** *(от человека, 2026-11-01; где — развёртывание `apps/ui/*`, конфиг веб-сервера; когда — спека деплоя/production; Claude, 2026-11-01)*
  Решение человека: каркас и микрофронтенды в production — статика одного nginx, каждый фронтенд в своей папке: каркас в корне, remote в `/mf/cabinet/`, `/mf/admin/`, `/mf/supervisor/` — те же пути, что в `federation.manifest.json`, код не меняется. Разделение по папкам оставлено, чтобы позже разнести отдельные модули на другие серверы или CDN: тогда меняется только адрес remote в манифесте или правило reverse proxy, origin для браузера остаётся один (cookie refresh и CSP без изменений). Что учесть:
  - деплой каждой папки независимый и атомарный (новая версия в новую директорию, затем переключение symlink или префикса); общий артефакт на все папки убирает смысл федерации;
  - кэш: чанки с хэшем — `Cache-Control: immutable`, а `index.html`, `federation.manifest.json` и `remoteEntry.json` — `no-cache`, иначе смешаются старый каркас и новый remote;
  - расхождение версий у открытых вкладок: shared-singletons со `strictVersion` могут не сойтись — дисциплина версий общих пакетов, сбой загрузки remote показывается «Раздел недоступен» (уже есть);
  - общий конфиг nginx — общая точка отказа; при разных командах — разграничение прав на выкладку папок;
  - dev-серверы `ng serve` на фронтенд (compose, `npm run ui:dev`) остаются только для разработки.

- [ ] **N-28. Production-почта identity: проанализировать `namshi/smtp`.** *(от человека, 2026-11-01; где — `compose.yaml` (сервис `mailpit`), `SMTP_URL` identity, `apps/identity`; когда — спека деплоя/production; Claude, 2026-11-01)*
  Mailpit только перехватывает письма для dev и в production не годится: письма подтверждения регистрации и приглашений должны доходить до настоящих ящиков.   - поддерживается ли образ (дата последнего релиза, известные уязвимости), точная версия тега;
  - режим: прямая отправка в MX против релея через smarthost (SES, Postmark, корпоративный SMTP) — без smarthost письма с нового IP почти наверняка уйдут в спам;
  - SPF, DKIM, DMARC для домена отправителя: где подписывается DKIM и как ключ попадает в контейнер (секрет, не в git);
  - TLS до smarthost, аутентификация, ограничение сетей-отправителей (релей не должен быть открытым), порт только во внутренней сети compose;
  - очередь и повторы при недоступности получателя, логи доставки;
  - сравнить с вариантом без своего релея: identity ходит напрямую в SMTP провайдера.
