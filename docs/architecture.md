# Архитектура кода Swag

Как устроен код платформы — общие правила для всех сервисов и приложений. Архитектура конкретного ядра (его порты, операции, модель данных) прорабатывается отдельно в спеке, где этот сервис появляется. Что строим и зачем — в [роадмапе](../AI_PLATFORM_ROADMAP.md), схема компонентов — в [architecture.svg](architecture.svg). Конкретные проверки этих правил — в [спеке 000](spec/000-foundation.md#42-правила-ядра-и-оболочки).

## Главный принцип: ядро отдельно от оболочки

Любой сервис и любое приложение Swag состоит из двух частей:

- **Ядро** — вся логика: алгоритмы, правила предметной области, расчёты, решения. Чистый TypeScript, который не знает, кто его вызывает и где он запущен.
- **Оболочка** — тонкий слой, который подключает ядро к конкретному способу входа: HTTP на Fastify, процесс в песочнице, UI на Angular или React, консольная команда, eval-прогон.

Одно ядро — сколько угодно оболочек. Ядро оркестратора можно загрузить в Fastify и дать к нему ручки API, а можно вызвать из консоли или из теста — поведение одинаковое. Ядро пользовательского приложения (авторизация, возможности, балансы, проекты, агенты) пишется один раз, а UI поверх него можно сделать на любом фреймворке.

Зачем так:
- **Тестируемость.** Ядро проверяется обычными юнит-тестами за миллисекунды, без HTTP, Docker и браузера.
- **Замена фреймворка — дешёвая.** Переход с Fastify на другой сервер или с Angular на React затрагивает только оболочку.
- **Несколько входов к одной логике.** API, консоль, eval-прогоны и будущие коннекторы вызывают одно и то же ядро, а не копию логики.
- **Агенту проще.** Граница проверяется автоматически, поэтому логика не расползается по контроллерам и компонентам.

## Пакеты

```
apps/<имя>/             оболочка
packages/<имя>-core/    ядро
packages/adapter-<технология>/   адаптер инфраструктуры
packages/contracts/     общие схемы и типы
packages/api-integration/  общая чистая логика ядер, работающих с API платформы; правила ядра
packages/config/        чтение env, только для оболочек
packages/helpers/       универсальные хелперы без зависимостей (`@swag/helpers`), серверные — `@swag/helpers/server`; ядра не импортируют
packages/adapter-openrouter/  источник цен OpenRouter на `fetch` (спека 004, 4.9)
packages/adapter-gateway-http/  регистрация роёв в llm-gateway для оркестратора на `fetch` (спека 004, 4.6)
```

У каждого пакета свой `README.md`: что он делает, какие задачи решает, ключевые решения и их причины, ограничения и связи. README описывает текущее состояние пакета и обновляется в той же задаче, что меняет пакет. Начинать знакомство с пакетом — с него.

Пара называется одинаково: `apps/orchestrator` подключает `packages/orchestrator-core`. Новая оболочка для того же ядра — новый каталог в `apps/`, ядро не меняется. Все пакеты — `@swag/<имя каталога>`.

| Ядро | Что внутри | Оболочки |
|---|---|---|
| `orchestrator-core` | Исполнение плана роя: песочницы, сети, ключи, accounts шины, уборка | `apps/orchestrator` (Fastify) |
| `llm-gateway-core` (спека 002) | Вызов модели через LLM Gateway: проверки запроса, каталог моделей, стоимость, событие `llm.call`, поток, сверка с апстримом | `apps/llm-gateway` (Fastify) |
| `api-core` | Координатор, рои, планы, расходы, доступ к данным пользователя по `Actor` | `apps/api` (Fastify) |
| `identity-core` (спека 012) | Пользователи, вход, сессии и токены, роли и права, блокировка, первый администратор | `apps/identity` (Fastify) |
| `billing-core` (спека 013) | Баланс по предоплате: пополнение, резерв бюджета роя, закрытие резерва по ledger | в MVP подключается в `apps/api`, позже свой сервис |
| `agent-core` | Агентный цикл, журнал инструментов, скиллы | `apps/agent` (процесс в песочнице) |
| `ui-core` (спека 001, остальное — 014) | Состояние и сценарии фронтендов платформы: вход, личный кабинет, админка, супервизор, рои | фронтенды в `apps/ui/*`: в 001 `apps/ui/cabinet` (Angular) |

**Фронтенды** лежат в `apps/ui/<имя>` (npm workspaces `apps/ui/*`), каждый собирается и деплоится независимо и может быть на своей технологии: `shell` — каркас с входом, подгружает микрофронтенды `cabinet`, `admin`, `supervisor`; `landing` — презентационная страница на Astro. Логика — в ядрах, фронтенд только рисует. В 001 есть только `cabinet` как самостоятельное приложение; каркас, способ сборки микрофронтендов и деление `ui-core` — спека 014 (D-11).

Одна оболочка может подключать несколько ядер: `apps/api` в MVP собирает `api-core` и `billing-core`. Вынести ядро в свой сервис — значит сделать для него новую оболочку и заменить в старой адаптер порта (вызов в процессе → HTTP или шина); само ядро и его вызывающие не меняются.

## Правила ядра

1. **Зависимости — только из белого списка**: `zod`, `@swag/contracts`, `@swag/api-integration`. Любое расширение — осознанное решение в спеке с обоснованием.
2. **Нет фреймворков и инфраструктуры**: ни Fastify, ни Angular, ни React, ни клиентов Postgres, NATS, Docker, S3.
3. **Нет окружения**: ни `node:*`, ни `process`, `Bun`, `Deno`, `window`, `document`; ядро не читает файлы и env. Ядро работает одинаково в Node, Bun и браузере.
4. **Всё внешнее — через порты.** Порт — интерфейс, который объявляет ядро: «мне нужно создавать песочницы» (`SandboxProvider`), «мне нужно текущее время» (`Clock`), «мне нужно сохранять рои» (хранилище). Ядро описывает, что ему нужно, а не как это сделано.
5. **Точка входа — фабрика** `create<Имя>Core(deps)`: принимает порты и настройки, возвращает объект с операциями. Без глобального состояния и синглтонов — два вызова фабрики дают два независимых ядра (удобно в тестах и для нескольких роёв в одном процессе).

## Правила оболочки

1. Читает конфигурацию, создаёт адаптеры, вызывает фабрику ядра.
2. Переводит вход (HTTP-запрос, аргументы команды, событие UI, сообщение шины) в вызов ядра, а результат — в ответ.
3. Не содержит решений, расчётов и правил предметной области. Если в контроллере или компоненте появилось «если … то …» про предметную область — это код ядра.

## Доступ: кто вызывает ядро

На платформе три роли: **пользователь** (свой кабинет, баланс, рои), **администратор организации** (`admin`, всё в своей организации) и **супервизор** (`supervisor`, владелец платформы — вся платформа). Модель организации — D-10. Пользователи, роли и права хранит сервис identity, он же выдаёт токены.

1. **Оболочка** проверяет токен: подпись и срок, без запроса в identity. Ключ проверки — через порт. Из токена оболочка собирает `Actor` — `userId`, роли, права — и передаёт его в операцию ядра. Нет токена или он неверен — ответ «не авторизован», ядро не вызывается.
2. **Ядро** решает, можно ли: операции с данными пользователя принимают `Actor` первым аргументом, проверяют право (`swarm.run`, `user.manage`, `balance.topup`…) и владельца данных. Чужое — ошибка «нет доступа», а не пустой ответ. Правило в ядре, а не в контроллере, поэтому оно одинаково для HTTP, консоли и тестов.
3. **Системные вызовы** (оркестратор → api) идут со служебным `Actor` своей роли, а не без проверки.
4. **Песочница и агент** токен пользователя и ключи провайдеров моделей не получают: агенту доступны только LLM Gateway (заголовки `x-swag-swarm-id`, `x-swag-agent-id`; ключ агента — спека 004) и шина роя. LiteLLM только переводит форматы, виртуальные ключи и бюджеты LiteLLM не используются (D-21).

Тип `Actor` и список прав — в `@swag/contracts`, общие для всех ядер.

## Адаптеры

Адаптер — реализация порта на конкретной технологии: `SandboxProvider` на dockerode, хранилище на Postgres, шина на NATS, HTTP-клиент LiteLLM (`adapter-litellm`, порт `LlmUpstream` ядра `llm-gateway-core`). Адаптеры лежат в отдельных пакетах `packages/adapter-<технология>`, а не внутри оболочки, чтобы одну реализацию могли использовать разные оболочки (сервис и консоль). Для тестов ядра пишутся простые адаптеры в памяти.

```
                 ┌─────────── оболочка ───────────┐
HTTP / CLI / UI →│ контроллер → фабрика ядра(deps) │
                 └───────────────┬────────────────┘
                                 │ вызов операций
                        ┌────────▼────────┐
                        │      ядро       │ объявляет порты
                        └────────┬────────┘
                                 │ интерфейс порта
                        ┌────────▼────────┐
                        │     адаптер     │ Docker, Postgres, NATS, S3, LiteLLM
                        └─────────────────┘
```

## Наблюдаемость: traceId, логи, трейсы

Каждый процесс прослеживается от запроса пользователя до сбоя (спека 016, раздел 7 роадмапа).

1. **Ядро** не знает OpenTelemetry. Оно пишет через порт `Logger` (`debug`, `info`, `warn`, `error`) и передаёт контекст — `swarmId`, `agentId`, ошибку в `err`. В логах `traceId` добавляет адаптер логгера из текущего контекста трассировки. Для конверта события ядро получает `traceId` через обязательный порт `TraceContext` и переносит его как непрозрачную строку: не создаёт и не интерпретирует (спека 016, Q-1).
2. **Оболочка** поднимает OpenTelemetry SDK, принимает контекст из входа (HTTP-заголовок `traceparent`, заголовок сообщения NATS, env `TRACEPARENT` в песочнице) или начинает новый трейс, открывает спан на операцию и вызывает ядро внутри него.
3. **Адаптеры** передают контекст дальше: HTTP-клиент — в заголовке, NATS — в заголовках сообщения, `SandboxProvider` — в env песочницы. Адаптер логгера пишет JSON-строку с `traceId` и `spanId` и отправляет её в Collector.
4. **События платформы** несут `traceId` в конверте: ядро, которое строит событие, берёт его из порта `TraceContext`, а `traceId` рождается в оболочке на триггере (запрос пользователя). Так событие из UI связывается с трейсом.
5. **Одна схема лога** во всех сервисах: `time`, `level`, `service`, `msg`, `traceId`, `spanId`, `swarmId`, `agentId`, `err` (тип, сообщение, стек). Тип записи — в `@swag/contracts`.

Куда уходит телеметрия: OTLP → OpenTelemetry Collector → Tempo (трейсы) и Loki (логи) → Grafana. Смена бэкенда — правка конфигурации Collector, не кода.

## Как это проверяется

- `npm run arch:check` — зависимости и импорты ядер против белого списка (спека 000, 4.5).
- `tsconfig` ядер без DOM и без `@types/node`: обращение к `process` или `window` — ошибка типов.
- Отсутствие логики в оболочках автоматически не проверить — это пункт ревью.
- Доступ: у каждой операции с данными пользователя есть тест «чужой `Actor` получает отказ».
