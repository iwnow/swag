# 🗺️ ФИНАЛЬНЫЙ ПОШАГОВЫЙ ROADMAP: AI-CRM Swarm Platform (SaaS)

Этот роадмап объединяет изначальный план AI-CRM Broker, механизмы изоляции вычислительных сред (MicroVM/Docker+CRIU), сквозную FinOps-аналитику токенов, продвинутый контур Observability & Health, а также концепцию самоисцеляющейся инфраструктуры на базе специализированных MCP-серверов.

---

## 🏗️ Общая архитектурная матрица платформы

Система разделена на независимые изолированные слои для обеспечения безопасности, масштабируемости и детерминизма:

1. **Центральный Координатор (Core Gateway):** Бэкенд на Fastify + Vercel AI SDK. Управляет логикой, сессиями пользователей (`tenantId`, `sessionId`), маршрутизацией запросов и оркестрацией агентов.
2. **Микросервис-Оркестратор Песочниц (Sandbox Provider):** Выделенный слой на TypeScript (Dockerode API), управляющий жизненным циклом изолированных Linux-сред (`node:20-alpine`) с ограничением ресурсов и поддержкой бинарной сериализации памяти (CRIU).
3. **FinOps & Business Контур (PostgreSQL + TimescaleDB):** Сервис точного биллинга токенов, истории сообщений, аудита действий и логов затрат с гарантией транзакционности (ACID).
4. **Infrastructure Observability & Health Контур (Prometheus + Grafana):** Независимый слой мониторинга «здоровья» серверной инфраструктуры, собирающий телеметрию CPU, RAM, Network I/O и OOM-Killed событий в реальном времени.
5. **Управляемый MCP-Слой (Managed MCP Gateway):** Безопасный шлюз интеграции с внешними системами клиентов и внутренней инфраструктурой без прямого доступа к продакшен-базам данных.

## 📅 Подробные этапы реализации проекта (0–8)

### Этап 0. Тест-лаборатория, Эвалы и Мокирование (Фундамент)
*Метрика: baseline-скор на golden dataset, 0ms сетевых задержек при локальном тестировании.*
- [ ] **Golden Dataset:** Подготовить тестовый набор из 50–100 кейсов техподдержки CRM, включая пограничные сценарии, синтаксические ошибки и prompt-инъекции.
- [ ] **Локальный инференс (Ollama):** Развернуть локально `llama3.2:3b` для проверки базовой логики и вызова инструментов, а также `deepseek-r1:1.5b` для тестирования цепочек рассуждений без затрат на API.
- [ ] **Семантический роутер (Math на клиенте):** Написать на чистом TypeScript функцию вычисления косинусного сходства векторов. Настроить кэширование эмбеддингов (`text-embedding-3-small`) для мгновенного перехвата базовых команд пользователя (`/clear`, `сбрось историю`, `status`) на стороне Node.js за ~50мс в обход тяжелой LLM.
- [ ] **Eval-харнесс и Трейсинг:** Интегрировать `promptfoo` в CI/CD пайплайн. Подключить `Langfuse` для отслеживания стоимости, latency и версионирования промптов на каждый вызов.

### Этап 1. Gateway, Роутинг и Structured Outputs (Мозги)
*Метрика: p95 до первого токена, 100% валидность генерируемого JSON.*
- [ ] **Vercel AI SDK и Fastify:** Реализовать бэкенд гейтвея, вынеся модели и провайдеров в динамические JSON-конфиги (без хардкода в коде).
- [ ] **Structured Outputs через Zod:** Жесткая валидация намерений пользователя, извлечения сущностей и классификации обращений.
- [ ] **Интеграция LiteLLM Proxy:** Запуск LiteLLM в Docker-контейнере рядом с гейтвеем для обеспечения автоматического балансирования нагрузки, обхода лимитов (Rate Limits) и мгновенного Fallback (переключение с DeepSeek на OpenAI GPT-4o в случае сбоя сети).

### Этап 2. Микросервис-Оркестратор Песочниц и Бинарный Resume (Среда выполнения)
*Метрика: Скорость холодного старта среды <500мс, время восстановления сессии <50мс.*
- [ ] **Разделение слоев:** Вынести управление рантаймом выполнения кода в изолированный микросервис на базе библиотеки `dockerode`.
- [ ] **Изолированные среды (Docker/WSL2):** Настройка создания контейнеров `node:20-alpine` под каждую уникальную сессию с лимитами `Memory: 512MB` и `CpuQuota: 50%` от одного ядра.
- [ ] **Бинарная сериализация памяти (CRIU):** Реализовать в оркестраторе эндпоинт `/freeze`, выполняющий команду `docker checkpoint create` для сброса состояния оперативной памяти воркер-процесса агента на диск. Написать логику эндпоинта `/start` с флагом восстановления `--checkpoint` для мгновенного оживления агента ровно в том же состоянии процессора и стека памяти.
- [ ] **Аварийные предохранители (Guardrails):** Внедрить в агентный цикл внутри песочницы счетчик `MAX_LOOPS = 5` и интерцептор бюджета (Cost Tracker), аварийно завершающий процесс с ошибкой `BUDGET_EXCEEDED` при обнаружении признаков зацикливания.

### Этап 3. Динамический Реестр Скиллов и Многоагентное Взаимодействие (Рой)
*Метрика: Процент успешно выполненных комплексных задач на eval-наборе.*
- [ ] **Стандарт SKILL.md:** Создать файловую структуру реестра скиллов в общем хранилище. Написать системный инструмент `activate_skill(name)`, который динамически считывает Markdown-инструкции навыка и инжектирует их в начало контекста LLM.
- [ ] **Резолв путей в песочнице:** Разработать модуль трансляции путей, который на лету преобразует относительные пути к скриптам автоматизации внутри папки скилла (например, `scripts/clean_data.js`) в абсолютные пути внутри изолированной среды контейнера, защищая систему от Path Traversal атак.
- [ ] **Шина обмена контекстом (Multi-Agent Swarm):** Реализовать логику Координатора, способного под сложную составную задачу параллельно разворачивать несколько песочниц (например, `Агент-Кодер` + `Агент-Тестировщик`) и передавать промежуточные результаты выполнения (World State) между ними.

### Этап 4. Безопасная интеграция с данными: Архитектура Managed MCP (Корпоративный слой)
*Метрика: Результат аудита безопасности, 0 прямых подключений к продакшен-БД клиентов.*
- [ ] **Вариант 1 (API Gateway через Swagger):** Написать модуль автоматического парсинга OpenAPI/Swagger JSON спецификаций клиентских CRM. Реализовать генерацию кода MCP-сервера через DeepSeek, преобразующую эндпоинты API в строго валидные инструменты агента.
- [ ] **Вариант 2 (Изолированная Read-Only Реплика):** Интегрировать механизм интроспекции схем данных (чтение таблиц и колонок). Реализовать безопасный генератор SQL-запросов «только на чтение» для работы агента с обезличенными зеркалами БД.
- [ ] **Вариант 3 (Локальный On-Premise MCP-Коннектор):** Разработать Docker-образ локального моста, который ставится внутрь закрытого контура компании, подключается к внутренней инфраструктуре локально и пробрасывает наружу в платформу только шифрованный текстовый SSE-туннель.

### Этап 5. Сервис Метрик, Аналитика и FinOps-Оптимизация (Деньги и Контроль)
*Метрика: Точность биллинга до 4-го знака после запятой, процент экономии бюджета в UI.*
- [ ] **Metrics & FinOps Collector:** Создать отдельный микросервис на Fastify + PostgreSQL с расширением **TimescaleDB** для сбора временных рядов (Time-Series) использования токенов.
- [ ] **Реализация Prompt Caching:** Оптимизировать структуру отправки массива `messages` так, чтобы тяжелые системные промпты и контент `SKILL.md` всегда находились в кэшируемом префиксе запроса, снижая затраты на ввод до 90%.
- [ ] **Smart Routing и Сжатие контекста:** Написать логику каскадного переключения моделей (простые шаги -> дешёвая модель, сложные тупики -> рассуждающая модель) и механизм сжатия истории (`Context Compaction`) через автоматическую генерацию Summary при превышении лимита в 10 000 токенов.
- [ ] **Финансовый API для UI:** Разработать эндпоинты для личного кабинета, отдающие метрики **Burn Rate** (скорость траты денег в минуту), затраты в разрезе конкретных сессий MicroVM и график чистой выгоды от оптимизаций.

### Этап 6. Инфраструктурная Наблюдаемость и Системный Мониторинг (Health & Observability)
*Метрика: Аптайм нод, скорость обнаружения аномалий ресурсов <5 секунд.*
- [ ] **Метрики контейнеров (Prometheus):** Настроить сбор метрик с Docker-демона и запущенных MicroVM в Prometheus (`container_cpu_usage_seconds_total`, `container_memory_usage_bytes`).
- [ ] **Отслеживание OOM-Killed событий:** Реализовать логику немедленного перехвата системных сигналов Linux об аварийном завершении процессов внутри песочницы из-за нехватки выделенной оперативной памяти (512MB).
- [ ] **Алертинг через Grafana:** Спроектировать дашборд системного мониторинга для разработчиков и настроить правила отправки критических алертов в Telegram/Slack при аномальном потреблении ресурсов хоста.

### Этап 7. Самоисцеляющаяся Инфраструктура через Инфра-MCP (Автономность)
*Метрика: Процент сбоев инфраструктуры, устраненных автоматически без участия человека.*
- [ ] **Интеграция Инфраструктурных MCP-серверов:** Подключить специализированные модули управления окружением (`Docker MCP Server`, `Prometheus MCP Server`) к внутреннему контуру платформы.
- [ ] **Изоляция прав (Least Privilege):** Жестко ограничить права доступа Docker MCP сервера на уровне сокетов, разрешив ИИ-инструментам управлять *только* контейнерами, имеющими префикс `agent-sandbox-*`, полностью закрывая доступ к системным базам данных и ядру платформы.
- [ ] **Сценарий Self-Healing (ИИ-Девопс):** Написать логику Агента-Наблюдателя. При фиксации падения рабочей песочницы по памяти (через Prometheus API), агент должен автоматически вычитать логи контейнера через Docker MCP, определить причину, динамически скорректировать лимиты RAM в конфигурации оркестратора и перезапустить сессию из бинарного чекпоинта CRIU.

### Этап 8. AI UX на Angular и Стратегия Flywheel (Интерфейс и Продакшен)
*Метрика: Доля принятых ответов без правок, глубина удержания пользователей.*
- [ ] **Интерфейс Swarm Console:** Разработать на Angular реалтайм-граф запущенных песочниц. Визуализировать состояния контейнеров: при переходе в спячку через CRIU иконка в UI должна переключаться в статус «Заморожен (Экономия RAM)».
- [ ] **Human-in-the-loop в UI:** Создать интерактивные карточки подтверждения действий. Если агент в песочнице через внешний MCP вызывает деструктивное действие (изменение статуса сделки, удаление данных), оркестратор блокирует операцию до физического одобрения пользователем в интерфейсе.
- [ ] **Пайплайн Flywheel и Оценка:** Сбор фидбека и «золотых правок» менеджеров. Интеграция механизма `Dynamic few-shot` для автоматического подмешивания успешных исторических примеров в реестр скиллов на основе их семантической близости.
