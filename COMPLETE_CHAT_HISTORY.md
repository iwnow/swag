# История проектирования: Архитектура AI-Агентов и Платформы Swarm-Песочниц

В данном документе собраны все ключевые этапы, архитектурные решения и концепты, спроектированные в ходе данной сессии для создания автономной B2B SaaS платформы многоагентных систем.

---

## 1. Концепция Agent Skills и Динамическая Загрузка Контекста

### Что такое Skill для агента
Скилл — это модульный набор инструкций, правил и ресурсов, оформленный в виде изолированной папки со входной точкой `SKILL.md` (стандарт описания навыков ИИ).
Структура папки навыка:
```text
skills/
└── data-analyzer/
    ├── SKILL.md            # Главные инструкции (YAML frontmatter + Markdown)
    ├── scripts/
    │   └── process_csv.js  # Скрипты автоматизации для песочницы
    └── templates/
        └── report.md       # Шаблоны документов и отчетов
```

### Принцип динамического контекста (Dynamic Context Loading)
Вместо загрузки всех имеющихся инструкций в контекстное окно модели сразу (что ведет к потере внимания и экспоненциальному росту стоимости токенов), платформа использует принцип прогрессивного раскрытия:
1. Базовый системный промпт Координатора содержит только краткие метаданные (названия и описания) доступных скиллов.
2. При получении сложной задачи модель вызывает универсальный системный инструмент `activate_skill(skill_name)`.
3. TypeScript-код на стороне сервера считывает полный Markdown-файл `SKILL.md` с диска и подмешивает его в массив `messages` (роль `tool`).
4. На следующем шаге модель выполняет задачу, обладая глубокими экспертными знаниями конкретного модуля. Для этого префикса автоматически срабатывает механизм контекстного кэширования (**Prompt Caching**), обеспечивая скидки до 90% от провайдеров (DeepSeek, OpenAI).

## 2. Архитектура Агентного Цикла (TypeScript + LiteLLM API Contract)

Модель общается с TypeScript-клиентом по строго фиксированному контракту. Существует 4 сценария ответа API, которые должен корректно обрабатывать агентный цикл:
1. **Прямой текстовый ответ:** `finish_reason: "stop"`, заполнен `content`. Модель сразу выдает ответ пользователю.
2. **Одиночный вызов инструмента:** `finish_reason: "tool_calls"`, массив `tool_calls` содержит 1 объект. Поле `content` равно `null`.
3. **Параллельный вызов инструментов (Parallel Tool Calling):** `finish_reason: "tool_calls"`, массив `tool_calls` содержит несколько объектов с уникальными `id`. Выполняются параллельно через `Promise.all`.
4. **Комбинированный ответ:** Модель одновременно выдает текст объяснения в `content` и массив `tool_calls` на выполнение действий.

### Изоляция провайдеров через LiteLLM Proxy
Для достижения абсолютной независимости кодовой базы от конкретных ИИ-провайдеров (DeepSeek, Anthropic Claude, OpenAI) в архитектуру внедряется **LiteLLM Proxy Server**. 
* LiteLLM работает как отдельный контейнер, полностью имитирующий OpenAI API.
* В коде на Node.js/TypeScript используется стандартная библиотека `openai` с перенаправлением на `baseURL` прокси-сервера.
* Смена моделей, балансировка нагрузки, управление API-ключами и автоматический отказоустойчивый переход (**Fallback**) на провайдера-дублера при ошибках 503 настраиваются в файле `litellm_config.yaml`, не требуя изменения TypeScript-кода агента.

## 3. Семантический Роутер на Клиенте (Эмбеддинги и Математика)

Чтобы не тратить ресурсы больших языковых моделей на обработку тривиальных или системных команд, на клиенте (Node.js) разворачивается **Семантический роутер (Semantic Router)**.
* Базовые фразы-синонимы (`"забудь всё"`, `"очисти чат"`, `"сбрось историю"`) один раз при старте переводятся в числовые векторы (эмбеддинги) через дешевую модель (например, `text-embedding-3-small`).
* Запрос пользователя на лету переводится в вектор, и на чистом TypeScript вычисляется **косинусное сходство** по формуле:
  $$CosineSimilarity = \frac{A \cdot B}{\|A\| \|B\|}$$
* Если коэффициент сходства превышает порог (например, `0.82`), выполнение мгновенно перехватывается на стороне TypeScript без вызова тяжелой LLM. Время ответа сокращается с 3-4 секунд до 50 миллисекунд.

## 4. Суверенные Песочницы (MicroVM) и Оркестратор

Для обеспечения безопасности «нулевого доверия» (Zero Trust) и автономности агентов, логика разделяется на два независимых слоя: **Координатор (Мозги на Node.js)** и **Оркестратор песочниц (Инфраструктура)**.

### Проблема сохранения состояния автономных агентов
Классического сохранения массива строк `messages` с привязкой к `session_id` в базу данных недостаточно для автономных агентов. При прерывании по лимитам или падении сервера теряется физическое состояние среды выполнения (World State): созданные файлы, запущенные компиляторы, сетевые сокеты. Более того, «зависшие» вызовы инструментов без ответов (`role: 'tool'`) ломают валидацию API при перезапуске.

### Решение: Бинарная сериализация памяти (MicroVM Checkpointing)
Индустриальным стандартом решения этой задачи является запуск агентских циклов внутри изолированных сред: **MicroVM на базе AWS Firecracker** (через облачные/self-hosted решения вроде **E2B SDK**) или в локальных контейнерах Linux с поддержкой **CRIU (Checkpoint/Restore in Userspace)** в WSL2 на Windows 10.
* По сигналу паузы или исчерпанию лимита итераций (`MAX_LOOPS`) оркестратор вызывает команду `docker checkpoint`.
* Вся оперативная память процесса (стек, регистры vCPU) и дифференциал диска сбрасываются в бинарные слепки памяти (`vm.state`) и привязываются к `session_id`.
* При возобновлении сессии контейнер оживает за сотые доли секунды ровно в том же системном такте процессора, на котором остановился. Для кода агента время замирает без потери состояния окружения.

## 5. Интеграция с СБ бизнеса (Managed MCP)

Чтобы решить главную проблему корпоративных клиентов — категорический запрет Службы Безопасности (СБ) на прямую передачу строки подключения (connection string) к продакшен-базам данных, платформа реализует три архитектурных шлюза через **Model Context Protocol (MCP)**:

1. **Коннектор к API Gateway (Интроспекция Swagger/OpenAPI):** Клиент предоставляет только JSON-файл документации своего корпоративного API и read-only токен. Платформа через DeepSeek «на лету» генерирует код MCP-сервера, преобразующий эндпоинты в безопасные инструменты для агентов.
2. **Изолированная Read-Only Реплика:** Подключение к предварительно замаскированному (обезличенному от персональных данных) зеркалу базы данных внутри изолированного периметра сети.
3. **Локальный On-Premise MCP-агент (SSE-туннель):** Клиент разворачивает контейнер-генератор MCP-серверов внутри своего закрытого контура. Контейнер подключается к локальной БД, а наружу в платформу отдает только зашифрованный веб-сокет (SSE-туннель), передавая исключительно текстовые результаты выполнения инструментов. Сами данные базу не покидают.

## 6. Двухконтурный Мониторинг (FinOps + Infrastructure Observability)

Платформа разделяет метрики для личного кабинета пользователя (FinOps-аналитика) и системного мониторинга администратора (Health & SRE).

### Контур 1: Финансовый учет (PostgreSQL + TimescaleDB)
Служит для расчета стоимости сессий и вывода графиков в UI на Angular. Использование Prometheus здесь исключено из-за отсутствия ACID-транзакционности и высокого риска потери финансовых данных при сетевых сбоях.
* **Метрики:** Количество потраченных токенов, чистая стоимость итерации на основе актуальных тарифов провайдеров, объем сэкономленных денег благодаря механизмам **Prompt Caching**, **Smart Routing** (каскадный даунгрейд модели до дешевой в зависимости от сложности шага) и **Context Compaction** (автономное сжатие истории сообщений через Summary-блоки при раздувании контекста).

### Контур 2: Инфраструктурная наблюдаемость (Prometheus + Grafana)
Служит для отслеживания технического здоровья серверов и контейнеров.
* **Метрики:** Потребление CPU ядра, RAM песочниц, сетевой трафик, фиксация OOM-Killed событий (превышение лимита памяти контейнера агента).
* **Самоисцеление через Инфра-MCP:** Подключение серверов `Docker MCP` и `Prometheus MCP` позволяет специализированному ИИ-агенту (SRE-девопсу) самостоятельно реагировать на триггеры Grafana: читать логи упавших контейнеров, автоматически увеличивать лимиты памяти в оркестраторе и бесшовно перезапускать песочницы из бинарных чекпоинтов без привлечения человека.

## 7. Полный Пошаговый Роадмап Платформы (От MVP к Production)

### ЭТАП 0: Тестирование, Эвалы и Мокирование (Лаборатория MVP)
* **Метрика:** Baseline-скор качества на Golden Dataset, Latency семантического роутера.
* **Инфраструктура:** Локальное окружение на **Ollama** (`llama3.2` + `deepseek-r1`) для бесплатных тестов. Математическая функция косинусного сходства на чистом TypeScript. Настройка регрессионных тестов промптов в CI через `promptfoo`.

### ЭТАП 1: Gateway, Structured Outputs и Провайдеры
* **Метрика:** Процент валидного JSON-вывода, p95 до первого токена.
* **Инфраструктура:** Сервер на **Fastify** с интеграцией **LiteLLM Proxy**. Динамические конфиги моделей. Жесткая валидация интентов и извлечения сущностей через **Zod**. Организация префиксов сообщений под Prompt Caching.

### ЭТАП 2: Реестр Скиллов и Агентный Луп
* **Метрика:** Точность вызова специализированного навыка, корректность резолва путей.
* **Инфраструктура:** Реализация универсального инструмента `activate_skill(name)`. Создание локального реестра `SKILL.md` файлов. Разработка транслятора путей для скриптов автоматизации внутри изолированных вычислительных сред.

### ЭТАП 3: Микросервис-Оркестратор и Бинарная Сериализация
* **Метрика:** Время заморозки/разморозки контекста, стабильность восстановления сессии.
* **Инфраструктура:** Вынос рантайма в отдельный сервис на базе **Dockerode**. Включение **CRIU** в WSL2. Реализация эндпоинтов `/freeze` и `/start --checkpoint`. Внедрение интерцептора бюджетов (Cost Tracker) и жесткого лимита `MAX_LOOPS = 5` для защиты от бесконечных зацикливаний.

### ЭТАП 4: Коннекторы Безопасности (Managed MCP) и Многоагентность
* **Метрика:** Доля успешной автоматической генерации MCP-серверов по Swagger-схемам.
* **Инфраструктура:** Модуль интроспекции внешних данных. Генератор TypeScript-кода MCP-серверов через DeepSeek. Реализация логики параллельного развертывания нескольких песочниц под задачу (**Multi-Agent Swarm**) и обмена контекстом между ними.

### ЭТАП 5: FinOps-Коллектор и UI на Angular
* **Метрика:** Доля принятых ответов агента без правок, точность финансовых графиков биллинга.
* **Инфраструктура:** Создание отдельного микросервиса аналитики и метрик на **PostgreSQL + TimescaleDB**. Разработка фронтенда на **Angular (Swarm Console)**: реалтайм граф состояний Docker-контейнеров (отображение спящих/активных MicroVM), графики Burn Rate и интерфейс безопасного апрува действий (**Human-in-the-loop**).

### ЭТАП 6: Инфраструктурный Observability & Health (Прод)
* **Метрика:** Уровень аптайма платформы, время автоматического устранения инцидентов.
* **Инфраструктура:** Развертывание связки **Prometheus + Grafana**. Сбор инфраструктурных логов контейнеров. Настройка Telegram-алертов для аномального поведения агентов.

### ЭТАП 7: Самоисцеление инфраструктуры (Инфра-MCP)
* **Метрика:** Процент инцидентов инфраструктуры, разрешенных автоматически без участия DevOps-инженера.
* **Инфраструктура:** Подключение `Docker MCP` и `Prometheus MCP` к ядру координатора. Внедрение SRE-агента для автоматического анализа логов упавших песочниц, динамического масштабирования ресурсов (RAM/CPU) и восстановления сред из бинарных слепков оперативной памяти.
