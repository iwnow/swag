# План MVP: платформа роёв агентов

Дата: 2026-10-21. Пересборка [AI_PLATFORM_ROADMAP.md](AI_PLATFORM_ROADMAP.md) с учётом замечаний из [AI_PLATFORM_ROADMAP_REVIEW.md](AI_PLATFORM_ROADMAP_REVIEW.md).

## Суть продукта

Пользователь ставит задачу. Платформа на лету собирает под неё рой агентов:
- каждый агент работает в своей песочнице (контейнер или microVM), песочницы поднимаются быстро;
- агенту подключаются скиллы из общего реестра — по смыслу задачи;
- агенты общаются через шину, изолированную на уровне роя: рой A не видит рой B;
- всё видно в UI, и главная метрика — **сколько денег тратится**, в реальном времени, по рою, агенту и шагу.

Коннекторы к внешним системам (CRM и др.) — следующий этап, после MVP.

## Критерии готовности MVP (given / when / then)

1. **Сборка роя.** Пользователь вводит задачу («разбери CSV с продажами, найди аномалии, напиши отчёт») → координатор возвращает план роя (роли, скиллы, связи, бюджет) → оркестратор поднимает N песочниц, и все агенты в статусе `running` меньше чем за 2 с с момента утверждения плана (из тёплого пула).
2. **Скиллы.** Каждому агенту смонтированы только скиллы из плана, read-only. Агент без скилла `csv-analysis` не видит его файлов.
3. **Шина.** Агенты обмениваются сообщениями. Сообщение из роя A не доходит до роя B — это проверено автотестом и на уровне сети, и на уровне шины.
4. **Деньги.** В UI видно стоимость в реальном времени: всего по рою, по агенту, по сообщению или вызову LLM. Сумма в UI совпадает со счётом провайдера за тестовый прогон с точностью ±1%.
5. **Бюджет.** Если рой превысил лимит, все его LLM-вызовы отклоняются, песочницы останавливаются, пользователь видит причину.
6. **Граф.** UI показывает рой графом: узлы — агенты со статусом и стоимостью, рёбра — сообщения шины.
7. **Уборка.** После завершения или отмены роя не остаётся контейнеров, сетей и учётных записей шины.

**Безопасность в MVP (что не должно сломаться):** у песочницы нет ключей LLM-провайдеров и нет выхода в интернет. Наружу открыт только LLM-прокси и шина. Код агента не может обойти учёт стоимости.

## Архитектура MVP

```
                ┌──────────────────────── Control plane ────────────────────────┐
  UI (Angular)  │  API / Coordinator ── Orchestrator ── Skill Registry          │
   граф, $  ◄───┤        │                   │                                  │
   WebSocket    │   Event Stream ◄──── LiteLLM Proxy (вирт. ключи, $, бюджет)   │
                │        │                   ▲                                  │
                │   Postgres (ledger, события, планы)                           │
                └────────────────────────────┼──────────────────────────────────┘
                                             │ только прокси + шина
        ┌──────── Swarm A (своя сеть, свой аккаунт шины) ────────┐   ┌── Swarm B ──┐
        │  [agent-1] ◄──► NATS account A ◄──► [agent-2]          │   │   ...       │
        │  /skills/x:ro                         /skills/y:ro     │   │             │
        └────────────────────────────────────────────────────────┘   └─────────────┘
```

### Ключевые решения

**1. LLM-прокси = LiteLLM: единый формат для цикла агента и центр учёта денег.**
Агентный цикл пишется **один раз** на OpenAI-совместимом API (`messages`, `tools`, `tool_calls`, streaming) — на любом языке, обычным OpenAI SDK. LiteLLM Proxy переводит этот формат в Anthropic, Gemini, DeepSeek и локальные модели. Модель агента — строка из плана роя (`model: "claude-sonnet"`), список моделей и провайдеров — в конфиге LiteLLM, а не в коде.

Агент в песочнице не ходит к провайдеру напрямую:
- оркестратор при старте агента выпускает в LiteLLM **виртуальный ключ** (`/key/generate`): `team` = рой, `metadata` = `swarmId`/`agentId`, `max_budget` = лимит агента, у команды — лимит роя, `models` = только модели из плана;
- агент получает `OPENAI_BASE_URL` и этот ключ, настоящих ключей провайдеров в песочнице нет;
- LiteLLM считает стоимость по `usage` (включая cached tokens) и пишет spend logs. Через callback платформа получает событие `llm.call` → ledger + стрим в UI;
- при превышении бюджета LiteLLM отклоняет вызов, а при завершении роя ключи удаляются (`/key/delete`).

Что проверить на этапе 1 (это гипотезы, а не факты):
- **Тарифы:** у LiteLLM своя таблица цен, она может отставать от провайдеров. Задать цены своих моделей явно в конфиге и сверить с биллингом провайдера.
- **Параллельность:** при параллельных вызовах агентов роя проверка бюджета может пропустить несколько запросов сверх лимита (гонка). Замерить; если перерасход недопустим — резервировать бюджет в оркестраторе.
- **Streaming:** при потоковой выдаче `usage` должен приходить (`stream_options.include_usage`).
- **Фичи провайдеров, которых нет в OpenAI-формате:** prompt caching Anthropic (`cache_control`), reasoning — проверить, что LiteLLM пробрасывает их и правильно считает за них стоимость.
- **Версия:** закрепить версию образа LiteLLM по digest, обновлять осознанно.

Учёт денег нельзя обойти из кода агента, и он одинаков для любого фреймворка внутри песочницы. Стоимость compute (секунды песочницы × тариф) — второй источник в том же ledger, её пишет оркестратор.

**2. Песочница — за интерфейсом, первая реализация на Docker.**
```ts
interface SandboxProvider {
  create(spec: SandboxSpec): Promise<SandboxHandle>; // image, cpu, mem, mounts, network, env
  exec(id: string, cmd: string[]): Promise<ExecResult>;
  stop(id: string): Promise<void>;
  stats(id: string): AsyncIterable<SandboxStats>;
}
```
- MVP: `DockerProvider` (dockerode) + рантайм gVisor (`runsc`), если хост на Linux. На Windows 10 / WSL2 для разработки — обычный `runc`.
- Скорость — за счёт **тёплого пула**: заранее созданные остановленные или приостановленные контейнеры из одного образа. Взять из пула + подмонтировать = десятки–сотни миллисекунд, без CRIU.
- Позже: `FirecrackerProvider` (нужен Linux с KVM). Перед тем как писать свой, оценить готовые self-hosted решения на Firecracker (например, E2B) — гипотеза, что их хватит. Проверить: развернуть, замерить старт и плотность.
- Лимиты: `NanoCpus`, `Memory`, `PidsLimit`, read-only rootfs + tmpfs `/work`, non-root, `no-new-privileges`, `CapDrop: ALL`.

**3. Шина: NATS с отдельным аккаунтом на рой плюс отдельная Docker-сеть на рой.**
- Сеть: `docker network create --internal swarm-<id>`. Внутри только агенты роя, выход только к прокси и NATS (через отдельный attach или sidecar). Между роями L3-связности нет.
- Шина: NATS, на каждый рой свой account с JWT, который выпускает оркестратор. Изоляция роёв делается на уровне шины, а не договорённостью о названиях subject.
- Subjects внутри роя: `agent.<agentId>.inbox`, `swarm.broadcast`, `swarm.state` (общее состояние — KV bucket JetStream).
- Почему не прямой p2p между контейнерами: через брокер каждое сообщение видно оркестратору. Отсюда граф в UI, аудит, лимиты частоты, повтор при падении агента.

**4. Рой генерирует координатор, исполняет оркестратор — детерминированно.**
Координатор (LLM) выдаёт **план роя** как structured output (Zod-схема):
```ts
SwarmPlan = {
  goal: string,
  budgetUsd: number,
  agents: { id, role, model, skills: string[], systemPrompt, limits: { maxSteps, maxUsd } }[],
  edges: { from, to }[],          // кто кому может писать
  entry: agentId, exit: agentId,
}
```
Оркестратор валидирует план (скиллы существуют, бюджет ≤ лимита пользователя, агентов ≤ N) и только потом поднимает песочницы. В MVP пользователь видит план и жмёт «Запустить» — заодно это защита от сжигания денег.

**5. Реестр скиллов — версионированные папки, выбор по смыслу.**
- Скилл: `skills/<name>/<version>/SKILL.md` (frontmatter: name, description, inputs, требования к образу) + `scripts/`.
- Выбор: координатору передаётся каталог (name + description). Если скиллов больше ~50 — сначала отбор top-k по эмбеддингам описаний, затем выбор LLM.
- Доставка: монтирование read-only в `/skills/<name>`. Транслятор путей не нужен.
- Prompt caching: системный промпт агента + его SKILL.md — неизменный префикс на всю жизнь агента, история идёт после него.

**6. Наблюдаемость — один поток событий.**
Все компоненты пишут события одного формата: `swarm.created`, `agent.started`, `llm.call` (tokens, $, latency), `bus.message`, `agent.failed`, `budget.exceeded`. Хранение — Postgres, UI получает поток по WebSocket. Prometheus/Grafana для хоста — отдельно и позже, это не продуктовая метрика.

**7. Состояние агента и возобновление (задача, которую в исходной идее решал CRIU).**
Проблема из [COMPLETE_CHAT_HISTORY.md](COMPLETE_CHAT_HISTORY.md) §4 реальная: одной истории `messages` мало, нужен ещё World State, а «зависшие» `tool_calls` без ответа ломают API при перезапуске. В MVP её закрываем без снимков памяти:
Состояние агента — четыре слоя, у каждого своё решение:

1. **Файлы — на диске, слепок памяти не нужен.** `/work` агента — отдельный Docker volume, а не слой контейнера: переживает остановку, удаление и пересоздание контейнера. На паузе и после каждого шага — снимок тома (`tar` → S3/MinIO, ключ `swarmId/agentId/step-N`). Это даёт перенос агента на другой хост и откат на шаг N, а в UI — «машину времени» по шагам. (`docker checkpoint` тома не сохраняет и сам требует неизменного диска.)
2. **История с моделью — Postgres.** Каждое сообщение цикла (assistant, tool) пишется до следующего шага.
3. **Процессы в памяти теряются — допустимо.** Агент не держит значимое только в памяти, всё пишет в файлы. Долгие процессы (dev-сервер, watch) скилл поднимает скриптом при старте.
4. **Внешний мир меняется — его не восстанавливает никто, включая CRIU.** Защиты:
   - **Уведомление о паузе:** при возобновлении цикл добавляет сообщение «пауза с T1 до T2, данные до паузы могли устареть — перед изменяющими действиями перечитай состояние».
   - **Оптимистичные блокировки:** инструменты записи принимают ожидаемую версию (`updatedAt`/ETag). Конфликт → агент перечитывает и решает заново. Защищает и от паузы, и от параллельных агентов.
   - **Общее состояние роя** — NATS KV с ревизиями, обновление через compare-and-set.
   - **Пропущенные сообщения** — устойчивые (durable) подписчики JetStream доставляют накопленное по порядку.

**Журнал выполнения инструментов (решает «висящие» `tool_calls`):**
- перед вызовом в БД пишется `tool_call_id = started`, после — результат;
- при возобновлении: результат есть → подставить его без повтора; только `started` и инструмент идемпотентный → повторить; только `started` и неидемпотентный → `role: tool` «результат неизвестен, проверь состояние»;
- во внешние системы `tool_call_id` уходит как ключ идемпотентности — повтор не создаёт дублей.

**Пауза** — только на границе итерации, после записи результатов инструментов.

**Песочница — одноразовый вычислитель, источник истины снаружи.** Её можно убить в любой момент и поднять заново (на этом или другом хосте) из Postgres + S3 на границе последнего шага. Потеря — максимум работа текущего шага.

| Данные | Где хранятся | Комментарий |
|---|---|---|
| Планы роёв, агенты, статусы | Postgres | |
| История сообщений с моделью | Postgres | Большие выводы инструментов (> ~32 KB) — в S3, в истории ссылка. |
| Журнал инструментов (`started`/результат) | Postgres | |
| События для UI и аудита | Postgres | |
| Ledger денег | Postgres | Целые микро-единицы. |
| Ключи, бюджеты, spend logs LiteLLM | Postgres (отдельная БД LiteLLM) | Callback дублирует расход в ledger. |
| Реестр скиллов | S3 (пакеты по версиям) + Postgres (каталог, эмбеддинги описаний) | В песочницу — read-only монтирование. |
| Рабочие файлы агента — живая копия | Docker volume на хосте | Только пока агент работает. |
| Рабочие файлы агента — снимки | S3/MinIO, `swarmId/agentId/step-N` | Восстановление, перенос, откат. Позже — инкрементальные (restic) вместо полного `tar`. |
| Итоговые артефакты роя (отчёты и т. п.) | S3 + запись в Postgres | Отдаются в UI. |
| Сообщения шины | NATS JetStream | Хранятся, пока жив рой. Копия в события Postgres — для графа и аудита. |
| Общее состояние роя | NATS KV | Ревизии, compare-and-set. При завершении роя — снимок в Postgres. |
| Секреты провайдеров | Конфиг/секреты LiteLLM, позже vault | В песочницу не попадают. |
| Внутри контейнера | ничего уникального | tmp, кэши пакетов. |

Если снимок памяти всё-таки понадобится (агенты с долгими живыми процессами), брать готовую паузу/возобновление microVM (например, persistence в E2B — проверить, что она есть в self-hosted версии и сколько занимает resume), а не CRIU в WSL2.

## Этапы MVP

| # | Этап | Результат (definition of done) | Размер |
|---|------|--------------------------------|--------|
| 0 | Каркас и eval | Монорепо, Postgres, схема событий и ledger, 10–20 эталонных задач для роя с ожидаемым результатом и потолком стоимости. | S |
| 1 | LiteLLM + учёт денег | LiteLLM в Docker, 2+ провайдера в конфиге, виртуальные ключи на агента/рой, callback → ledger и стрим. Один и тот же тестовый цикл на OpenAI-формате работает на всех моделях конфига. Бюджет отклоняет вызовы. Сверка с биллингом провайдера ±1%. | M |
| 2 | Оркестратор песочниц | `SandboxProvider` на Docker, тёплый пул, лимиты, сеть на рой, гарантированная уборка (reaper по TTL). Замер: старт из пула < 500 мс. | M |
| 3 | Один агент end-to-end | Образ агента: универсальный цикл на OpenAI-формате (OpenAI SDK → LiteLLM) + клиент шины. Цикл покрыт тестами на 4 сценария ответа: только текст, один `tool_call`, параллельные `tool_calls`, текст + `tool_calls`. Возобновление после остановки с починкой висящих вызовов (решение 7). Задача → результат, стоимость видна. Смена модели — только строка в плане. | M |
| 4 | Реестр скиллов | Формат SKILL.md, каталог, read-only монтирование, выбор top-k + LLM. | S |
| 5 | Шина и рой | NATS-аккаунт на рой, план роя от координатора, валидация, запуск N агентов, обмен сообщениями, автотест изоляции A/B. | L |
| 6 | UI | Ввод задачи → просмотр плана → запуск → живой граф (статусы, сообщения) + панель денег: рой / агент / вызов, burn rate, остаток бюджета, кнопка «Стоп». | M |
| 7 | Прогон eval и стабилизация | Все эталонные задачи проходят в пределах бюджета. Падение агента не валит рой. Отчёт: стоимость и качество роя против одного агента. | M |

Порядок 1 → 2 → 3 выбран намеренно: деньги считаются с первого же вызова LLM, а не достраиваются в конце.

## Что сознательно НЕ входит в MVP

- CRIU, заморозка и восстановление памяти. Состояние агента = история в БД + `/work` на томе + починка висящих вызовов (решение 7).
- Self-healing ИИ-девопс с доступом к Docker-сокету. Реакция на падения — детерминированная политика оркестратора.
- TimescaleDB, Langfuse. LiteLLM + Postgres закрывают нужды MVP. Langfuse можно подключить позже как ещё один callback LiteLLM для трейсов. Источником денег при этом остаётся ledger.
- Firecracker — после MVP, за тем же интерфейсом `SandboxProvider`.
- Мультитенантный SaaS-биллинг, оплата, тарифы — после MVP. В MVP один-несколько доверенных пользователей.

## После MVP: коннекторы к внешним системам

1. **Connector Gateway (MCP).** Коннектор — MCP-сервер в своей песочнице, вне сети роя. Агенты вызывают его инструменты через шину или gateway, а не напрямую. Транспорт — Streamable HTTP.
2. **Генерация из OpenAPI** — детерминированный генератор, LLM только улучшает описания инструментов. Секреты клиента — в vault, в песочницу агента не попадают.
3. **Права и подтверждения.** Каждый инструмент размечен: `read` / `write` / `destructive`. `write` и `destructive` по умолчанию требуют подтверждения в UI (HITL). Это **обязательное условие** до первого подключения к реальной CRM.
4. **On-prem мост** для закрытых контуров: исходящее соединение от клиента, mTLS, подписанный образ.
5. **Мультитенантность и ПДн:** изоляция данных тенантов, выбор провайдеров LLM с учётом 152-ФЗ, сроки хранения, аудит.

## Главные риски

| Риск | Чем закрыть |
|------|-------------|
| Рой дороже и не лучше одного агента | Этап 7: сравнение на eval. Координатор может решить, что рой не нужен, и запустить одного агента. |
| Агенты зацикливаются в переписке и жгут деньги | Бюджет на рой и на агента в прокси, лимит сообщений на ребро, `maxSteps` в плане. |
| Docker недостаточно изолирует сгенерированный код | gVisor в MVP на Linux-хосте, Firecracker после. Без сети наружу и без секретов в песочнице. |
| Утечка песочниц и сетей | Reaper по TTL + метка `swarmId` на всех ресурсах + тест «после роя ресурсов 0». |
