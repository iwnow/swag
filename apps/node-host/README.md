# @swag/node-host

Оболочка песочницы узла (спека 026, 4.8). Процесс в контейнере `swag-node-host:dev` принимает один вызов узла по кадрам stdin, исполняет код узла и отдаёт результат кадрами stdout. Оркестратор создаёт такую песочницу на каждый вызов (4.9, T-13), здесь она не запускается сама.

## Задачи

- Принять кадр `invoke` из stdin и только его до запуска кода: до `invoke` в stdout ничего не пишется.
- Запустить код узла в дочернем процессе `child.ts`, передать ему пакет, определение, вызов, настройки, секреты, данные прокси и дедлайн по IPC.
- Переслать `log`, `state.get`, `state.set` от узла оркестратору кадрами; ответы `state` и `abort` вернуть узлу.
- Строки stdout узла превратить в кадры `log` уровня `info`, строки stderr — в `warn`.
- Отдать итог кадром `result`. Если узел завершился без итога, — `result` с `node_failed` и текстом `child exited <code|signal>`.

## Что внутри

- `src/main.ts` — родитель: читает stdin построчно, валидирует `HostFrame` (`@swag/contracts`), запускает дочерний процесс через `fork` с `stdio: ['ignore', 'pipe', 'pipe', 'ipc']`, пересылает кадры в обе стороны. Каждый кадр — одна строка, один `process.stdout.write`.
- `src/child.ts` — дочерний процесс: `await import(package)`, проверка `type` и `version`, `parseSettings`, `NodeContext` (`secrets`, `http`, `log`, `state`, `signal`), вызов `invokeNode` из `@swag/node-sdk/runtime`. `NodeError` становится `result` с его кодом, прочие исключения — `node_failed`.
- `test/node-host.test.ts` — AC-026-20: запуск `src/main.ts` через `child_process.spawn` и три сценария: эхо, фикстура с логами и `state.get`, фикстура с `process.exit(3)`.
- `test/fixtures/` — два узла для теста. Подключаются по `file:` URL в поле `package`, поэтому `src` под тест не меняется.
- `Dockerfile` — образ по образцу `apps/agent`: пользователь `node`, команда `node apps/node-host/src/main.ts`, без сборки.

## Ключевые решения

- **Вывод узла не попадает в протокол.** Код узла работает в `child.ts`, его `console.*` и `process.stdout` уходят в pipe дочернего процесса и становятся кадрами `log` уровня `info`. Протокол защищён от случайного вывода, но не от намеренного обхода: граница доверия — контейнер.
- **`result` ждёт закрытия дочернего процесса.** Родитель пишет итог по событию `close`, поэтому строки stdout и stderr, пришедшие до итога, уходят раньше него. После итога процесс ставит `exitCode = 0` и закрывает stdin, а не вызывает `process.exit()`.
- **Дочерний процесс завершает себя сам.** После `result` он ждёт сброса канала IPC и stdout/stderr, затем `process.exit(0)`. Иначе незакрытые соединения `ProxyAgent` удерживали бы процесс и итог не ушёл бы родителю.
- **Прокси — через `undici`.** `fetch` и `ProxyAgent` берутся из одного пакета `undici` (версия `8.12.3`, точная). Глобальный `fetch` Node не принимает dispatcher из другой версии `undici`. Проверка `https:` и `egressMatches` идёт до запроса; отказ — `NodeError('egress_denied')`.
- **Дедлайн в дочернем процессе.** Сигнал узла прерывается по `abort` от родителя, по разрыву IPC и по `deadlineMs` из `invoke`. Оркестратор всё равно шлёт `abort` (4.10); собственный таймер нужен, чтобы узел не работал дольше своего дедлайна, даже если `abort` задержится.
- **Данные лога сериализуются через JSON.** Циклические или несериализуемые значения теряются, вызов `ctx.log` не падает.
- **Кадр до `invoke` или не JSON — отказ без итога.** Процесс пишет причину в stderr, ставит `exitCode = 1` и не пишет `result`: оркестратор увидит это как `protocol_error` (REQ-026-12). Кода `protocol_error` в `SandboxFrame` нет (4.1), поэтому кадр с ним не формируется.
- **Некорректные IPC-сообщения ребёнка не пересылаются.** Оркестратор их всё равно не примет по схеме; родитель пишет `log warn` и идёт дальше.

## Ограничения

- Лимиты кадров, длин `msg` и `message`, число записей `log` — на стороне оркестратора (4.8, 4.10). Родитель их не применяет.
- Таймаут вызова родитель не ведёт сам: это работа оркестратора (`abort`, затем удаление песочницы).
- Сбой прокси или сети внутри узла — ошибка `fetch` с текстом библиотеки, без отдельного кода.
- Повторный `invoke` и кадры, не относящиеся к моменту, игнорируются с записью в stderr; отказа с `protocol_error` нет (см. «Ключевые решения»).
